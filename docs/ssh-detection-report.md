\# SSH 반복 로그인 실패 탐지 보고서



\- 실습 일자: 2026-09-21

\- 프로젝트: Mini SOC

\- 분석 대상: 로컬 Docker SSH 서버



\## 1. 목적



SSH 인증 실패 로그에서 반복적인 로그인 시도를 탐지하고,

이벤트 생성부터 로그 수집, 탐지, 자동 검증까지 구현한다.



\## 2. 실습 환경



| 항목 | 구성 |

|---|---|

| 작업 환경 | Windows CMD |

| 컨테이너 환경 | Docker Desktop, WSL2 |

| 대상 서버 | Debian 기반 OpenSSH 컨테이너 |

| 접속 주소 | 127.0.0.1:2222 |

| 탐지 코드 | Python 3.12 |

| 이벤트 생성 | Paramiko |

| 자동 테스트 | unittest, GitHub Actions |



PC RAM 8GB와 Docker 할당 메모리 약 3.7GB를 고려해

첫 버전은 SSH 컨테이너와 Python 탐지기로 구성했다.

Wazuh 연동은 구현하지 않았으며 추후 확장 항목이다.



\## 3. 시나리오



\### 수동 검증



1\. labuser 계정으로 정상 로그인한다.

2\. Accepted password 로그를 확인한다.

3\. 잘못된 비밀번호를 3회 입력한다.

4\. Failed password 로그와 탐지 결과를 확인한다.



\### 자동 재현



scripts/run\_demo.py가 다음 작업을 수행한다.



1\. Docker를 통해 서버 공개 호스트 키를 읽는다.

2\. 해당 키로 접속 대상 서버를 검증한다.

3\. 실행마다 고유한 미등록 계정을 생성해 인증 실패를 3회 유발한다.

&#x20;  계정을 서버에 실제로 등록하지는 않는다.

4\. 실행 시작 이후 로그 중 해당 계정의 인증 실패만 추출한다.

5\. 탐지기에 전달하고 실패 3건, 경보 1건인지 확인한다.



접속 대상은 127.0.0.1:2222로 고정했다.

이번 실습은 인증 실패 패턴 재현이며, 계정 탈취는 수행하지 않았다.



\## 4. 탐지 규칙



| 항목 | 기준 |

|---|---|

| 대상 이벤트 | Failed password |

| 집계 기준 | 로그에 기록된 출발지 IP |

| 시간 범위 | 현재 실패 이벤트 기준 이전 60초, 경계 포함 |

| 임계값 | 실패 3회 이상 |

| 정상 로그인 | 실패 횟수에서 제외하며 기존 횟수는 초기화하지 않음 |

| 경보 발생 | 횟수가 임계값 미만에서 이상으로 바뀔 때 |

| 실행 방식 | 기존 로그 일괄 분석 |



IP별 deque에 실패 시각을 저장하고,

새 실패 이벤트마다 60초보다 오래된 기록을 제거한다.



3회/60초는 실습용 기준이다.

실제 운영에 적용하려면 정상 사용 패턴을 분석해 조정해야 한다.



\## 5. 실제 관측 결과



\### 정상 로그인 로그



```text

Accepted password for labuser from 172.18.0.1 port 42484 ssh2

```



\### 자동 재현 결과



```text

\[DEMO] Expected login failure 1/3

\[DEMO] Expected login failure 2/3

\[DEMO] Expected login failure 3/3

\[ALERT] Repeated SSH login failures ip=172.18.0.1 count=3 window=60s time=2026-09-21T06:28:41.356725+00:00

\[SUMMARY] failed\_logins=3 alerts=1

\[PASS] Attack simulation -> logs -> detection

```



출력 시각의 +00:00은 UTC를 의미한다.



172.18.0.1은 이번 Docker 환경에서 서버가 관측한 출발지 주소다.

이를 외부 공격자의 실제 주소로 해석하지 않는다.



실패 이벤트 3건에서 경보 1건이 발생함을 확인했다.

이 결과만으로 실제 공격 여부나 운영 환경의 탐지율을 판단할 수는 없다.



\## 6. 자동 테스트 결과



| 테스트 | 기대 결과 | 결과 |

|---|---|---|

| 실패 2회 | 경보 없음 | 통과 |

| 60초 내 실패 3회 | 경보 1건 | 통과 |

| 0초·30초·61초에 실패 | 오래된 기록 제외, 경보 없음 | 통과 |

| 0초·30초·60초에 실패 | 경계 포함, 경보 1건 | 통과 |

| 서로 다른 IP로 분산된 실패 | IP별 집계, 경보 없음 | 통과 |

| 실패 2회와 정상 로그인 1회 | 경보 없음 | 통과 |

| 60초 내 실패 4회 | 경보 1건 유지 | 통과 |



로컬에서 7개 테스트가 통과했다.

동일 테스트를 실행하는 GitHub Actions도 성공했다.



GitHub Actions는 탐지 로직을 검사한다.

실제 SSH 컨테이너를 통한 자동 재현은 로컬에서 검증했다.



\## 7. MITRE ATT\&CK 연관성



\- 전술: Credential Access

\- 기술: T1110.001 — Password Guessing

\- 참고: https://attack.mitre.org/techniques/T1110/001/



반복적인 SSH 인증 실패는 비밀번호 추측 시도에서 관측될 수 있다.

이번 규칙은 그 징후를 탐지하기 위한 기초 규칙이다.



자동 재현은 미등록 계정의 인증 실패를 발생시킨 것으로,

실제 비밀번호 추측 공격 전체를 검증한 것은 아니다.

반복 실패만으로 공격을 확정하지 않는다.



\## 8. 한계와 개선 방향



\### 오탐 가능성



\- 정상 사용자의 연속된 비밀번호 오입력

\- 오래된 비밀번호를 사용하는 자동화 프로그램

\- 같은 NAT 주소를 공유하는 여러 사용자의 실패 합산



\### 미탐 가능성



\- IP별 60초 내 실패가 3회 미만인 느린 시도

\- 여러 IP로 분산된 시도

\- 현재 정규식과 다른 형식의 인증 로그



\### 구현 한계



\- 로그가 시간순으로 입력된다고 가정한다.

\- Docker 로그 시각을 사용하며 별도 SSH 이벤트 시각을 추출하지 않는다.

\- 실행 간 탐지 상태를 저장하지 않아 재분석 시 같은 경보가 발생한다.

\- 로그 회전으로 삭제된 과거 이벤트는 분석할 수 없다.

\- 정상 로그인 전후의 실패를 연계하는 분석은 구현하지 않았다.

\- 자동 재현은 해당 실행의 로그만 선택하므로 혼합 트래픽 검증은 아니다.



\### 개선 계획



\- 경보를 JSON 형식으로 저장

\- IP와 계정을 함께 고려하는 추가 규칙 구현

\- 실패 후 성공한 로그인에 대한 상관분석

\- 실시간 수집과 중복 이벤트 처리

\- 자원 확보 후 Wazuh 연동



\## 9. 재현 방법



저장소 루트에서 Docker Desktop과 SSH 서버가 실행 중인지 확인한다.



```bat

docker compose up -d --build

```



Python 가상환경이 없다면 생성한다.



```bat

python -m venv .venv

```



의존성을 설치하고 자동 재현 및 테스트를 실행한다.



```bat

.venv\\Scripts\\python.exe -m pip install -r requirements.txt

.venv\\Scripts\\python.exe scripts\\run\_demo.py

.venv\\Scripts\\python.exe -m unittest discover -s tests -v

```



자동 재현에는 labuser 비밀번호 설정이 필요하지 않다.

수동 정상 로그인을 재현하려면 별도로 비밀번호를 설정한다.



```bat

docker compose exec ssh-server passwd labuser

ssh labuser@127.0.0.1 -p 2222

```
